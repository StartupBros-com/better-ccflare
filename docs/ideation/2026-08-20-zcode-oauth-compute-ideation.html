Can ZCode OAuth compute feed better-ccflare?

Yes, probably through a much smaller seam than a new provider: ZCode 0.16.3 already turns OAuth into a durable Z.ai API key and points it at the Anthropic endpoint better-ccflare already supports. The unresolved question is economic, not transport: does that key debit the same free or promotional allowance visible inside ZCode?

Evidence before options

Grounding Context

Codebase Context

better-ccflare already registers a zai provider with Anthropic Messages transport, streaming, model mapping, API-key storage, quota polling, and Z.ai-specific rate-limit reset parsing. Existing account storage can also hold OAuth access/refresh/expiry data, while Qwen and Codex provide non-Anthropic OAuth precedents.

Installed ZCode Evidence

The local ZCode CLI is version 0.16.3. Its bundle runs server-mediated OAuth, retains a Z.ai access token and ZCode JWT, exchanges the Z.ai token for a business token, creates or reuses zcode-api-key, and writes a normal Z.ai provider pointed at https://api.z.ai/api/anthropic.

External Context

Z.ai officially documents Claude Code and the Anthropic endpoint for GLM Coding Plan. GLM-5.3 supports low, high, and max; Claude Code xhigh maps to upstream max. Independent integrations have reproduced the OAuth-to-key path, including one reported live GLM-5.2 response.

Load-bearing Unknown

ZCode also carries a JWT and knows a separate plan gateway. Current reports disagree about which surface pays from which allowance, and the private gateway is device/captcha protected. A successful model response therefore proves transport only—not that the intended free, plan, bonus, or PAYG bucket funded it.

Repository Learnings

Rate-limit scope, duration, and evidence must name the same capacity window; uncertainty should choose a narrower and shorter hold. Provider behavior must be checked against live payloads rather than fixtures alone.

Policy Boundary

Z.ai’s Coding Plan is personal, coding-only, and limited to supported tools; its terms prohibit sharing, resale, and providing the benefit to third parties. A loopback-only single-user route reduces operational exposure but does not itself make better-ccflare an officially supported tool.

Measured on this account, 2026-08-20

Live Findings

Verdict: contradicted for the free tier. The free GLM-5.3 allowance is bound to a ZCode JWT on the private zcode.z.ai gateway, and that gateway refuses inference from a non-ZCode client. better-ccflare’s Z.ai provider talks only to api.z.ai/api/anthropic, where this account has no entitlement. No plan units were consumed while establishing this.

The entitlement is a Start Plan, not a Coding Plan

The account carries an active zcode-v3-start-plan-0817 “ZCode Start Plan” granting 3,000,000 GLM-5.3 units and 2,000,000 GLM-5-Turbo units per day, read from the gateway’s own billing endpoint. The desktop runtime selects builtin:zai-start-plan/GLM-5.3 at thoughtLevel: max.

Two credentials, two different worlds

Local provider state holds a 231-character JWT pointed at zcode.z.ai/api/v1/zcode-plan/anthropic (enabled, carrying the free plan) and a separate 49-character durable key pointed at api.z.ai/api/anthropic and flagged coding_plan_not_entitled.

ccflare’s exact path is unentitled

Calling the same quota endpoint better-ccflare polls, with the durable key, returned success: false and 当前用户不存在coding plan (“user has no coding plan”) with zero limit rows. A routed request there could only fail or draw on pay-as-you-go funds.

The gateway is device-gated

One minimal, unspoofed Anthropic-format request to the gateway with the valid JWT returned 400 with {"code":3007,"msg":"captcha verify failed"}; the key-header form returned 401. Reaching the free tier from another client would require defeating that verification, which this project will not do.

Consumption stayed at zero

Across every probe, GLM-5.3 remained used_units: 0 of 3,000,000, and the local ZCode database recorded no completed model turn. The daily window also rolled over mid-investigation, which is why paired before/after counters must sit inside one period.

What this changes

Idea 1’s proof ladder resolved early and negatively for the free tier; idea 2 should not be built for it; idea 7 is no longer speculative but blocked by an explicit provider control. A purchased GLM Coding Plan is the one path that makes the existing provider work unchanged.

1. Two-stage Entitlement Proof Ladder

Entitlement fidelityComplexity: LowConfidence: 90%

Use one real interactive ZCode turn as the control, recording every visible plan, quota, bonus, and paid-balance counter before and after. Then manually import or copy the durable zcode-api-key that ZCode already provisions, send one tiny user-initiated request force-routed through better-ccflare’s existing zai account, disable all failover, and compare the same counters after propagation. The test lane self-disables and remains quarantined unless the intended bucket moves and prohibited wallets do not.

Basis
direct: the existing provider already accepts a Z.ai API key and polls quota, while installed ZCode 0.16.3 independently derives a durable key for the same Anthropic endpoint. The repo’s live-payload learning explicitly rejects inferring billing identity from a successful response.
Rationale
This settles the only question that determines architecture. If counters match, the desired compute may already be one account-add away; if they do not, an OAuth implementation that emits the same key would be wasted work.
Downsides
One test can consume a small amount of paid balance, counters may lag or quantize, and concurrent ZCode traffic can contaminate the comparison. The experiment needs a quiet window, repeated snapshots, and a deliberately tiny request.
2

2. OAuth-to-Key Enrollment Adapter

Authentication lifecycleComplexity: MediumConfidence: 68%

After idea 1 proves bucket equivalence, add a login-only Z.ai onboarding surface that mirrors ZCode’s setup-time behavior: server-mediated OAuth, Z.ai business login, organization/project resolution, and create-or-reuse of a better-ccflare-named durable key. Persist the resulting key as an ordinary zai account, record whether it was created or reused, and leave runtime inference on the mature provider path. The account commits only after a bounded validation; abort never revokes a reused ZCode-owned key.

Basis
direct + external: the installed ZCode bundle contains this exact derivation flow; provider OAuth registration and durable credential fields already exist in better-ccflare; oh-my-pi merged the same shape, and gajae-code reported a live response with the derived key.
Rationale
The high-leverage seam is credential enrollment, not transport. Isolating OAuth from the hot path avoids a second refresh/auth regime in streaming, retry, and load-balancing code.
Downsides
ZCode’s OAuth and business endpoints are not the public Coding Plan integration contract, upstream details can change, and better-ccflare is not currently a named supported tool. Keep it opt-in and local until Z.ai approves or documents the flow.
Gate: do not build this if the manually imported key in idea 1 does not debit the desired entitlement.

3. Entitlement-Aware Account Twins

Entitlement fidelityComplexity: HighConfidence: 82%

Stop treating every credential for one Z.ai identity as fungible. Materialize manual PAYG, Coding Plan, OAuth-minted, bonus-backed, and any future plan-JWT surfaces as separate route identities carrying acquisition origin, endpoint, observed quota source, verified funding bucket, evidence freshness, and unknown → verified → drifted state. New twins are explicit-route-only until evidence promotes them; retries cannot cross wallets merely because the provider name matches.

Basis
direct: today the account row holds generic credentials, endpoint, mappings, and billing_type, while Z.ai usage has only broad time/token windows. Current JWT-versus-key reports demonstrate that two credentials from one login can have different economic behavior.
Rationale
This creates a reusable abstraction for every provider where subscription, promotional, and PAYG capacity coexist. It makes economic provenance part of route identity instead of an operator memory.
Downsides
Requires database changes in both SQLite and PostgreSQL, UI/CLI semantics, routing eligibility changes, and a migration strategy for existing opaque Z.ai accounts. It is excessive for a one-user proof unless other subscription integrations will reuse it.
4

4. GLM-5.3 Max Conformance Gate

Transport fidelityComplexity: MediumConfidence: 88%

Define “GLM-5.3 xhigh” as a behavior contract, not a model alias. Certify each exact credential × endpoint tuple for upstream model identity, 1M context, Claude Code xhigh → max, streaming event order, incremental tool arguments, stop events, system/cache behavior, and usage accounting. Initially admit only the official Anthropic Messages endpoint; an OpenAI-compatible route earns a separate certificate rather than becoming an opportunistic fallback.

Basis
external + direct: Z.ai’s current GLM-5.3 guide documents the model, 1M context, and effort conversion. The existing native provider streams through the official endpoint; the repo’s OpenAI converter uses a different reasoning shape and therefore cannot be presumed semantically equivalent.
Rationale
The user values maximum reasoning inside an agent loop. Plain text success can hide downgraded thinking, broken tool assembly, missing cache behavior, or an incorrect context window.
Downsides
Requires a live non-Anthropic request and exact upstream observations. Tests must obey the repo restriction against scripted Anthropic traffic and should use the user’s Z.ai account only through a deliberate force-routed canary.
5

5. Direct Claude Code Z.ai Launch Profile

Policy containmentComplexity: LowConfidence: 85%

If forwarding subscription traffic through better-ccflare remains policy-ambiguous, invert the integration: better-ccflare selects the credential and produces an ephemeral Claude Code launch profile, but Claude Code connects directly to Z.ai’s documented Anthropic endpoint. The profile pins GLM-5.3, 1M context, and model mappings, and it stays separate from the normal multi-provider pool.

Basis
external: Z.ai explicitly lists Claude Code as supported and publishes its configuration. A direct connection removes the unnamed intermediary from the data plane while retaining useful account-selection and launch ergonomics.
Rationale
This may deliver nearly all of the user value with lower technical and policy risk if “inside the same ccflare pool” is less important than easy access to the compute.
Downsides
It does not provide seamless per-request load balancing or failover through better-ccflare, and it still needs a usable key. It is a sibling launch lane, not a true provider integration.
6

6. Official Z.ai Support Gate

Policy containmentComplexity: Low codeConfidence: 72%

Before making the feature generally available, ask Z.ai to list better-ccflare as a supported local coding tool, provide a documented client registration, or grant written permission for a single-user local intermediary. Supply a narrow technical brief: loopback-only deployment, owner-only credentials, Claude Code request shape, no resale, and no bypass of provider controls.

Basis
external: Z.ai’s current usage policy restricts Coding Plan benefits to supported tools, and its subscription terms prohibit unsupported general integration and providing access to third parties. The docs show no established public app-registration process, so approval is an external dependency rather than an assumed API.
Rationale
Official support converts a fragile private integration into a durable product surface and eliminates the largest nontechnical uncertainty.
Downsides
Z.ai may not respond, may decline, or may require product changes. This does not unblock a same-day personal experiment, but it should gate upstreaming or distributing the feature.
7

7. Distinct ZCode JWT Lane (contingent only)

Auth + transportComplexity: HighConfidence: 28%

If—and only if—the proof ladder shows that the desired free promotion exists exclusively behind the ZCode JWT plan gateway, keep it separate from ordinary zai. A future lane would need its own endpoint, credential lifecycle, quota source, conformance certificate, and policy status. It should proceed only after Z.ai publishes or approves the contract; better-ccflare must not reproduce, bypass, or automate the gateway’s captcha/device controls.

Basis
external: current reverse-engineering reports show a separate JWT gateway and plan balance surface, while installed ZCode retains a JWT alongside the durable key. Those reports also show device/captcha enforcement and unresolved refresh/entitlement semantics.
Rationale
Separating the identity is architecturally honest if the promotion truly cannot be reached by a normal key. It preserves the option without contaminating the supported provider.
Downsides
Private unstable endpoints, unclear refresh, high operational burden, explicit provider controls, and weak policy footing. This is a stop sign unless official documentation or approval arrives—not an implementation recommendation.
